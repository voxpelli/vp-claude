# UPSTREAM: vp-beads

Friction, feature requests, and contribution opportunities against the
[vp-beads](https://github.com/voxpelli/claude-beads) plugin's skills and
tooling, discovered while building vp-knowledge.

## Feature Requests

- **backlog-groomer: multi-agent swarm mode for large backlogs, plus an adversarial close-gate before presenting closure candidates** (2026-07-01) — `/vp-beads:backlog-groomer` (workflows 1 and 3) triages sequentially: one agent runs `bd list`/`bd stale`/`bd blocked`/`bd find-duplicates` and reads issues in turn. A 2026-07-01 vp-knowledge session hand-orchestrated a different shape over 173 non-closed beads — a Haiku swarm followed by an Opus refutation pass — and it surfaced things a single sequential agent plausibly wouldn't reach in one context window:
  1. **Wave 1 (breadth):** N cheap-model agents, round-robin partition (not contiguous slices — a priority-sorted `NR % N` split gives every agent a representative cross-section, so verdicts stay comparable across agents) over the non-closed issue set; each reads its slice via `bd show` and classifies NEXT/LATER/STALE/CLOSE?/BLOCKED.
  2. **Wave 2 (verify):** re-partition thematically (by epic/subsystem, cutting across wave-1's round-robin) and re-run, but this time each agent checks wave-1's guesses against ground truth — grep the repo, read the schema/config file, check `git log`/branch state — not just re-reading the bead. This is where the real value concentrated: it confirmed a feature branch was 18 commits ahead of main while its beads still showed 2/27 done, and caught an inverted-looking `bd` dependency read that (see point 3) turned out to itself need re-checking.
  3. **Adversarial close-gate before presenting to the user:** a single stronger-model agent (Opus vs. the swarm's Haiku) whose only job is to refute the close-list, re-reading each candidate's FULL acceptance criteria (not just the field the swarm's evidence cited) and re-running the swarm's own ground-truth checks independently. This caught 2 live false-closes (a bead whose upstream dependency shipped but whose own in-repo retirement edits were undone; a check that gates 1 of 5 claimed surfaces by design) and refuted 2 of the verify-wave's own "corrections" — including a `bd dep tree <epic-root-id>` run that returned flat/no-deps and got over-generalized to "this epic's blocking is all soft prose"; `bd dep tree` on the root alone is empty precisely because the root has no deps of its own, while its children (confirmed via `bd blocked`, which IS graph-wide and reported the real chains correctly) carried genuine wired dependencies. Workflow 2 step 3's phrasing ("If `bd dep tree` is available, use it to visualize blocking power") reads as a `bd blocked` substitute; worth clarifying in the skill that `bd dep tree <id>` on a container/epic id is not equivalent to `bd blocked` and can look deceptively clean.
  4. A final synthesis pass pooled cross-chunk duplicates (round-robin splits scatter an epic's children across every wave-1 chunk; only a whole-set pass catches "these 4 beads are the same shipped feature filed 4×") and reported the _real_ backlog size (this run: 173 nominal → ~35 actually live once stale/closeable/deferred-with-trigger are separated out) — a number workflow 1's per-issue table doesn't currently surface.
  Suggested shape for vp-beads: an opt-in "swarm mode" for workflow 1 on large backlogs (some threshold, e.g. >50 open issues), and — regardless of swarm vs. sequential — folding a second-opinion refutation step into workflow 3 (Suggest closures) before candidates are shown to the user, since a close is a mutation that silently strands tracked work if wrong (asymmetric cost vs. a false LATER/STALE call). Known constraint if a swarm mode is built: bursting many agent launches at once can trip a provider-side admission throttle distinct from rate limits — cap concurrent launches to a handful, not one-shot-all-N.
  Ownership: shared · Workaround: none — currently reproduced by hand-orchestrating agents per session; the existing skill's sequential single-agent workflows remain the checked-in default.

## Bugs

- **`bd close` persistence broken when `.beads/` is gitignored** (2026-05-18) — Regular `bd close <id>` reports `✓ Closed` success but state reverts to `IN_PROGRESS` on next `bd show`/`bd stats`/`bd blocked`. Auto-export step emits warning `Warning: auto-export: git add failed: ... .beads ignored by gitignore`, which seems to roll back the JSONL write. `bd close --force` succeeds in-memory and the success message persists in that invocation, but the close ALSO doesn't reliably persist across subsequent `bd` invocations in this configuration. Reproduced 2x on Sprint 24 (vp-claude-lgb + vp-claude-cuz). Both issues continue to appear in `bd blocked` and `bd stats` as `IN_PROGRESS` despite multiple `--force` closes. This is a data-integrity issue: closed work appears unfinished, leading to false-positive blocked-dependency reports and incorrect sprint-tracking metrics.
  Severity: degraded · Ownership: upstream · Workaround: partial — `--force` succeeds in the current shell invocation but doesn't persist; verify every close with `bd show <id>` and accept some closes won't stick. Tracked locally as bd `vp-claude-syw`.

- **retrospective skill: commit-range command silently collapses to zero commits when RETRO files are gitignored, not "full history" as documented** (2026-07-03) \[degraded\] — Step 2's "Recent commits since last retro" command is `git log --oneline "$(git log -1 --format=%H -- RETRO-*.md)"..HEAD --no-merges`. The skill's own inline comment claims both "no prior RETRO files" and "RETRO files are gitignored" edge cases resolve identically to a full-history range ("In both cases the inner git log returns empty, making the range '..HEAD' which shows all commits"). This is factually wrong: when the inner command returns an empty string, the resulting range is literally `""..HEAD`, and `git log --oneline ""..HEAD --no-merges` empirically returns **zero commits**, not full history — confirmed on vp-claude (RETRO-\*.md is gitignored per `.gitignore:6`) where the same repo's unrestricted `git log --oneline --no-merges` shows 321 commits but the documented command returned none. Every retrospective on a project with gitignored RETRO files silently gets an empty "commits since last retro" section — including a genuine Sprint 1, where the comment claims this "correctly" shows full history but it doesn't. Workaround used this session (vp-claude Sprint 40): fell back to the previous RETRO file's on-disk mtime as a `--since` anchor, which only works because the file still exists locally with an accurate mtime — it would fail entirely on a fresh clone with no local RETRO history.
  Severity: degraded · Ownership: upstream · Workaround: partial — file-mtime fallback works only when the previous RETRO file is still present on disk; no anchor exists on a fresh clone. Suggested fix: the two edge cases need different handling — "no prior RETRO files" (genuine first retro) should fall back to an explicit unrestricted `git log --oneline --no-merges`; "RETRO files exist but are gitignored" has no git-based anchor at all and needs either a documented alternative (file mtime, or a sentinel git tag/note written at each retro) or an explicit warning that commit-range detection is degraded rather than silently returning empty.

- **upstream-tracker: bracket-severity template needs an escaping note for remark/markdownlint repos** (2026-07-04) \[minor\] — Workflow 1's documented entry formats show the optional severity tag unescaped: `**Short title** (YYYY-MM-DD) [blocking|degraded|minor] — ...`. In a repo with `remark-lint`'s `no-undefined-references` rule enabled (this repo's `check:md`), an unescaped `[degraded]`/`[blocking]`/`[minor]` in prose is parsed as a shortcut reference link with no matching `[text]: url` definition, and `remark --frail` fails the build. Confirmed by grep: every other UPSTREAM-\*.md entry in this repo that uses a bracket severity tag already escapes it as `\[degraded\]`/`\[minor\]` (e.g. `UPSTREAM-vp-beads.md`'s own retrospective-skill bug entry) — the workaround is already established in practice, just undocumented in the skill's own template text, so a fresh entry (mine, logged the same session) reproduced the break immediately.
  Severity: minor · Ownership: upstream · Workaround: full — escape the bracket tag as `\[severity\]` in any repo running remark/markdownlint with reference-link checking enabled; the skill's entry-format examples should show the escaped form (or note the caveat) so this isn't rediscovered per-project.

- **bd v1.1.0 schema migration panics on drifted TEXT storage, write-locking the database** (2026-07-07) \[blocking\] — After Homebrew auto-upgraded `beads` 1.0.5 → 1.1.0, all bd **writes** fail (`bd create`, `bd config unset`, `bd migrate`) while reads still work. bd v1.1.0's remote-migrate gate (#4259) first refuses the 4 pending v49→v53 schema migrations on a remote-backed DB; but the migration itself then **panics** — `rekey aux row ids: events: invalid hash length: 19` — on drifted adaptive-TEXT storage, so removing the remote lifts the gate yet the next write re-triggers migrate-on-open and crashes again. Root cause (corrected 2026-07-28 — the original entry said the Dolt pin _predates_ the dolthub/dolt#11126 fix, which is wrong): bd pins Dolt 2.1.4 (commit `1bf533220ab0`, 2026-06-05), which is **136 commits ahead** of #11126's merge commit `02564b0b` (2026-05-30), `behind_by: 0` — the fix is present. The real gap is dolt#11205, which names 2.1.4 explicitly as still panicking, closed later by Dolt 2.1.10 (2026-06-26). Adaptive out-of-line TEXT written by an earlier version is unreadable; rows "not repairable via SQL". Blocks all issue creation/updates for this project. Upstream: <https://github.com/gastownhall/beads/issues/4380> (exact events-table crash, fix "skip-and-warn per table" filed 2026-07-07; see also gastownhall/beads#4590 and #4353).
  **Fix shipped in beads 1.1.2 (2026-07-26)** — commit `564049bb`, the skip-and-warn-per-table approach. Two cautions, both verified rather than inferred. (1) It lets the database **open**; it does not repair drifted `events` rows, and the commit's own closing line is _"Not exercised against real drifted storage."_ (2) The commit message credits "Dolt 2.1.10" and bd's "migration 0057" as the mitigations, and **neither is in the released artifact**: the Dolt pin is byte-identical at v1.1.0 and v1.1.2 (still 2.1.4), and migration `0057_events_value_columns_idempotent_longtext` 404s at both tags — v1.1.2 tops out at 0053. **Independently re-verified 2026-07-29** (this was a second-order claim — an assertion about what a commit message claims — so it was re-checked from primary source rather than trusted): `go.mod` pins `github.com/dolthub/dolt/go v0.40.5-0.20260605230755-1bf533220ab0` identically at both tags, and the migrations tree tops out at `0053_repair_rig_wisps` at both, with no `0057_*` file at either. Upstream #4380 was still OPEN on 2026-07-28 despite the fix shipping.
  Severity: blocking · Ownership: upstream · Workaround: partial — reads still work; unblock either by upgrading to `beads` 1.1.2 (the local install is now on it), downgrading to 1.0.5 (no v49→v53 migration), or reinitializing a fresh v53 DB and reimporting the JSONL export. **Still marked blocking**: whether this machine's database actually migrated is unverified, and 1.1.2 only guarantees the DB opens. Full backup preserved at `.beads/backup-pre-local-2026-07-07.jsonl`.
